## C. コーディング上の回帰リスク

### C-1. 学習履歴とデータベース

- 現行 `DB_NAME="history-master-sample-v1"` は旧学習履歴の継続のため維持。`DB_VERSION=6` は新ストアを含むため**理由なく下げない**。
- IndexedDBストアの既存キー、`profile`、`revision`、`questionId`、`session.key`等の互換性を保つ。
- 回答確定は`saveAnswer()`で複数ストアへ一つのトランザクションとして反映。連続タップ・二重付与が起きないこと。
- 問題の論理削除は原則復元可能。既存回答・カードまで物理削除しない。
- 本番/テストのデータを混同しない。通常起動時は本番プロフィール。
- バックアップの検査・プレビューと保存は別。復元は双方のプロフィールを置換するため、実機での試験は**バックアップを用意した安全なテスト端末**で行う。

### C-2. 問題JSON

- 通常新規追加 `schemaVersion:1` と一括更新 `questionUpdateFormat:"history-master-question-update"` を混ぜない。
- `difficulty`/`tag`は新規制作時に付ける。古い取り込みデータの省略は許容し「未設定」と表示する。
- 正解配列は選択肢の**ID文字列**を参照。複数正解は全一致判定。元の選択肢IDが`A`でも、書き出しマスターで`"1"`等に再採番される仕様を尊重する。
- 更新前に`baseRevision`・`baseHash`を照合。**ハッシュを手で書き換えない**。更新後の重複・競合を全件チェックし、1件のエラーで全体を止める。
- 問題文の改行空白のみと、意味の変わる実質変更を区別。後者は当該問題の現行習得だけに影響し、旧回答履歴は保持する。
- JSON仕様書の時代ID・フィールド名を推測で増減しない。問題追加自体は別Workが担当し、ゲーム側で勝手に教材問題を作成しない。

### C-3. UI・アセット・学習報酬

- iPhone幅でカード、レーダー、管理画面、クレーンが横に切れないこと。
- 問題文/選択肢/解説の改行、80文字以上の読み物の表示、タッチ対象の大きさを保つ。
- `assets/`（複数形）を使用。カード: `cards/E01.webp`〜`E10.webp`、金貨: `coins/crown-gold.webp`、ぬいぐるみ: `plush/`以下。大文字小文字・拡張子を変えない。
- E01〜E10のカードテーマは`CARD_SUBJECTS`に対応。画像差替え・イラスト変更は明示依頼時のみ。
- コイン初回報酬・復習報酬の重複防止、プロフィール分離、クレーン消費・再開・景品保存を確認。確率やコストを勝手に変更しない。
- 操作アニメーションは`prefers-reduced-motion`にも配慮し、読解を妨げない。

## E. iPhone/iPad Safariの実機テスト（ユーザーへ依頼）

自動テストが通っても、以下は実機で確認が必要。**公開前・公開後のどちらで確認するか**も報告する。

1. **端末幅・タッチ:** iPhone縦画面/iPad画面で各種ボタンが押せ、左右スクロールや表示切れがない。
2. **長文問題:** 日本語改行・段落・選択肢折返しが読みやすく、スクロールや採点ボタンの配置が自然。
3. **回答/中断:** 問題を選ぶ途中・結果表示中に画面を離れても、再表示後に安全に再開できる。
4. **プロフィール分離:** 保護者テストで回答しても本番理解度やコインが変化しない。
5. **ファイル取り込み:** iPad/iPhone「ファイル」アプリから非公開の正常な10問JSONを読み込み、プレビュー後に追加できる。
6. **問題更新の安全性:** 実運用データでは事前にバックアップ。更新と復元の破壊的テストは本番端末・本番データで行わない。
7. **カード/画像:** E01〜E10のロック画像・拡大・時代名、金貨とクレーン景品のWebP表示を確認。
8. **報酬/クレーン:** 本番とテストで料金・残高・景品が正しく分かれ、タップ時に誤動作しない。
9. **公開反映:** GitHub Actionsのbuild/deployが成功し、Pagesの公開URLで最新版が表示される。キャッシュ問題はデプロイ遅延と切り分ける。
10. **PWA:** 今後PWAを実装した場合に限り、ホーム画面・オフライン・更新キャッシュを別途確認する。

## F. レビュー/公開ルール

1. Codexは**初めに調査と変更方針を提示**する。安全な小変更なら実装できるが、仕様変更・データ移行は先に承認を得る。
2. 作業は原則**新しいブランチ**で実施し、Pull Requestに差分を載せる。`main`へ勝手にマージしない。
3. PRの説明に必ず「目的 / 対応仕様 / 変更ファイル / データ互換性 / テスト結果 / 未実施項目 / Safariでの確認方法」を記す。
4. 必要に応じて開発チャットでPR差分の妥当性をレビュー。問題作成Work側でゲーム仕様を独自変更しない。
5. ユーザー承認後に`main`へマージ。GitHub Pagesの公開状態はActions成功と公開先の実動作を確認して報告する。
6. リグレッションが見つかった場合、既存学習データ保護を最優先にロールバック/再改修を検討する。データの初期化で手早くごまかさない。
