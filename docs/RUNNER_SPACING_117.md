# Issue #117 — iPhone縦のランナー下部余白

基点: 最新main `d1ac4f3`（PR #125マージ済み、v1.7.41）。ブランチ: `fix/117-runner-portrait-spacing`。APP_VERSION/親子配信識別子をv1.7.42に更新。

## 原因と方法の比較

AGENTS.md、REQUIREMENTS、DECISIONS_AND_TESTS、Issue #117、マージ済みPR #103/#115/#121/#123/#125を確認した。#103の非同期読込/復帰での位置維持、#121の新規入場時だけ先頭表示、iPad横64px/16px、#123の残高1箇所、#125の記録一覧を維持する。

アプリCSSを変える前にローカルChromium・合成DBで全状態を測定。子は`height:auto; min-height:100dvh; align-content:start`で上詰め。Canvas・ボタン間に余った高さを配っていない。親85dvhの空間を子のmin-heightが満たすため、操作・通知の終端より大きい余白が残る。Issue記載の旧267.59pxと今回281.55pxとの差は最新mainのタイトル非表示等を含むレイアウトによる。今回の比較は同じ最新mainを基準とする。

- **親iframe高さをCSSで調整（採用）**: 幅480px以下・縦画面だけ`calc(56.25vw + 17.5rem + env(safe-area-inset-top) + env(safe-area-inset-bottom))`。iframe読込前から高さが決まり、ゲーム状態・非同期保存では変わらない。高さでは分岐しないためアドレスバー伸縮だけでも予算は変わらない。
- **子min-height/余白だけ調整**: 親85dvhが残るため解決しない。子の上詰め・通常paddingを維持。
- **実寸のJS同期**: 不要。保存通知/結果/文字の非同期変化やスクロールへの影響が増えるため採用しない。

通常のviewportとCanvasの幅差90pxを見込み、Canvasの16:9から幅依存の高さを算出。実測の操作・HUD・通知・padding必要高に余裕を含め17.5remとした。375pxでは既存Canvas最低高160pxによる幅補正もある。480pxより広い端末、横画面、無料デモ/試遊は既存ルールを使う。UA判定はないため同じ幅条件の小型ブラウザにも適用される。

通知を含めた必要高まで無理に詰めず、通常文字で保存失敗通知の終端＋下paddingの後ろに約15〜16pxを残す。Safe Areaは子の既存paddingに加えて親の予算にも加算。固定高をoverflow:hiddenで切る変更はなく、文字拡大・極小表示は必要なdocumentスクロールを許す。
